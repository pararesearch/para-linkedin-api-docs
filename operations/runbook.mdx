## Provision Barada

Run against the target environment once:

```bash
npm run provision:barada
```

The script provisions or locates:

- `Barada Sahu`
- `barada@getmason.io`
- forced-change temporary dashboard password
- owner API key
- Akhil extension runner grant
- Akhil effective comment-persona mapping

Capture one-time credentials from the secure operator terminal and deliver them through an approved secret-sharing channel. They are not recoverable from PostgreSQL or logs.

Do not create a registration during account provisioning. Verify zero Barada requirements, search tasks, and runs before handoff.

## Verify extension pairing

Confirm an active grant from Akhil's owner ID to Barada's owner ID for `linkedin`, then confirm the existing Akhil extension device is online. Do not pair a second Barada device.

For compiler rollout, create a temporary Barada registration with `use_case`,
`auto_activate: true`, and a public HTTPS receiver. Search logs by its request
ID. Expect compilation queued/started/completed, plan activated, exactly ten
task queued events, and ten extension claim/persist/complete sequences.

For the complete live smoke, configure the production GitHub environment secrets and dispatch `LinkedIn Real Chrome Extension Smoke`, or run:

```bash
LINKEDIN_PUBLIC_API_URL=https://para-linkedin-api.onrender.com \
LINKEDIN_BARADA_API_KEY=... \
LINKEDIN_REAL_E2E_WEBHOOK_URL=https://receiver.example.com/linkedin \
npm run test:e2e
```

The script never opens Chromium and never inserts post rows. It waits for the installed extension ID `memidhnoiniadgfomefhmcahjcekkddd`, archives its temporary registration afterward, and writes redacted evidence under `real-extension-e2e/artifacts/`.

The production workflow also sets `LINKEDIN_REAL_E2E_REQUIRE_RECEIVER_INSPECTION=true`. It fails unless the receiver inspection endpoint returns the raw callback and headers needed to verify the HMAC and exact polling-payload equivalence.

Its dedicated receiver must reset per webhook ID and respond `500`, `429` with
bounded `Retry-After`, exceed the 10-second timeout, then return `200`. The
workflow allows 90 minutes for ten serial real-extension searches and the real
retry schedule.

## Recover a webhook

1. Read the delivery and attempt history.
2. Check response status, timeout, SSRF validation, and the receiver's signature verification.
3. Correct the receiver.
4. Replay only when status is `DEAD_LETTER`.
5. Reconcile the immutable batch through polling.

## Rotate secrets

Webhook secret rotation returns the new value once and increments `webhook_secret_version`. API-key rotation returns a new plaintext key and revokes the selected old key. Update consumers before discarding either one-time response.
