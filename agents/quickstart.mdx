This is the first page an API agent should read. The same owner-scoped Bearer key
can operate LinkedIn and Reddit registrations when it has the required generic
scopes.

## Bootstrap algorithm

1. Read the handoff and identify `platform`, `mode`, `external_id`, topics,
   webhook destination, and allowed mutations.
2. Read the API key from `PARA_API_KEY`. Do not echo or serialize it.
3. Call `GET /health/ready`. Stop on a non-`2xx` response.
4. Load OpenAPI and select only operations under the requested platform prefix.
5. List registrations and reconcile by `external_id` before creating anything.
6. For each mutation, persist one operation-specific `Idempotency-Key` before
   sending the request.
7. Treat create as configuration only. Call activate only when the handoff
   authorizes collection and supplies topics plus a public HTTPS webhook.
8. Treat run execution as asynchronous. Poll status with bounded intervals and
   stop when the requested runs are terminal.
9. Consume the immutable batch from the webhook or batch polling endpoint.
10. Return a redacted checkpoint containing IDs, states, counts, and request IDs.

A manual run does not bypass `delivery_time`. Use the handoff deadline and stop
with a resumable checkpoint instead of polling indefinitely.

## Environment

```bash
export PARA_SOCIAL_API="https://para-linkedin-api.onrender.com"
export PARA_API_KEY="set-this-outside-the-agent-transcript"
```

Never place the key in a URL, command history, generated file, test artifact, or
final report.

## Choose a workflow

| Goal | Workflow | Minimum scopes |
| --- | --- | --- |
| Inspect existing state | [LinkedIn](/agents/linkedin) or [Reddit](/agents/reddit) read path | `registrations:read` |
| Create or update a draft | Platform workflow manage path | `registrations:read`, `registrations:write` |
| Activate and request collection | Platform workflow run path | `registrations:read`, `registrations:write` |
| Consume final results | [Webhook consumer](/agents/webhooks) | `batches:read`; add `deliveries:read` for diagnostics |
| Replay a failed delivery | Webhook recovery path | `deliveries:read`, `deliveries:write`, explicit approval |
| Change credentials | [Authentication](/authentication) | `keys:manage`, explicit approval |

## Request rules

Send a caller-generated request ID on every request:

```http
Authorization: Bearer ${PARA_API_KEY}
X-Request-ID: agent-run-20260729-001
```

Add `Idempotency-Key` to creates and lifecycle actions. A good key identifies one
logical operation and remains stable across transport retries:

```text
create:reddit:customer-pain:v1
activate:reddit:customer-pain:v1
run:linkedin:founder-workflows:2026-07-29
```

Never reuse one key for a different body or operation.

## Retry policy

| Result | Agent action |
| --- | --- |
| `2xx` | Accept and persist the returned checkpoint |
| `400`, `409`, `422` | Fix the request; do not repeat unchanged |
| `401` | Stop and request a valid credential |
| `403` | Stop and request the missing scope |
| `404` | Refresh owner-scoped state; do not infer cross-owner existence |
| `429` | Honor bounded `Retry-After`, then retry with the same idempotency key |
| `5xx` or transport failure | Retry with bounded exponential backoff and the same idempotency key |

## Completion conditions

A collection request is complete only when:

- each requested run is terminal and successful;
- a `READY` immutable batch exists for the target delivery date;
- the stored payload is available through polling, even if `posts` is empty;
- webhook delivery is `DELIVERED`, or polling has been accepted as the recovery
  path; and
- the final report includes request, registration, run, batch, and delivery IDs
  when available.

Read [Agent handoff](/agents/handoff) before accepting an operator task.
