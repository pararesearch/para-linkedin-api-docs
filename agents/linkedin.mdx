LinkedIn collection is performed asynchronously by the paired real Chrome
extension. The API agent controls registration state and observes results; it
does not scrape LinkedIn itself.

## Preconditions

- Read [Agent handoff](/agents/handoff).
- Require `registrations:read` for inspection.
- Add `registrations:write` for create, patch, activate, pause, restore, run, or
  webhook test.
- Compiler-native creation requires a detailed `use_case`; activation requires a
  ready ten-search plan and a public HTTPS webhook.
- Use a stable `external_id` supplied by the operator.

## State machine

```text
list -> reconcile -> create with use_case -> compile -> inspect ten-search plan
     -> auto-activate -> ten extension runs -> terminal cycle -> READY batch
     -> verify DELIVERED webhook or accept polling recovery
```

Topics-only legacy creation does not queue work. `use_case` creation queues
compilation and may auto-activate after plan and webhook validation.

## Reconcile

```bash
curl --fail-with-body \
  "$PARA_SOCIAL_API/v1/linkedin/registrations?limit=100" \
  --header "Authorization: Bearer $PARA_API_KEY" \
  --header "X-Request-ID: linkedin-agent-reconcile-001"
```

Match `external_id` exactly. If it exists, patch only handoff-provided fields. If
it does not exist and create is approved, create one registration.

## Create

```bash
curl --fail-with-body \
  --request POST "$PARA_SOCIAL_API/v1/linkedin/registrations" \
  --header "Authorization: Bearer $PARA_API_KEY" \
  --header "Content-Type: application/json" \
  --header "X-Request-ID: linkedin-agent-create-001" \
  --header "Idempotency-Key: create:linkedin:founder-workflows:v1" \
  --data '{
    "name": "Founder workflow discussions",
    "external_id": "founder-workflows",
    "use_case": "Find firsthand B2B SaaS founder and revenue-leader posts about adopting AI agents in go-to-market workflows. Prioritize implementation details, measurable outcomes, buying friction, and unmet needs. Exclude job listings and event promotions.",
    "auto_activate": true,
    "delivery_time": "17:00",
    "timezone": "Asia/Kolkata",
    "webhook_url": "https://hooks.example.com/linkedin"
  }'
```

Capture `registration.id`. Send the one-time `webhook_secret` directly to the
approved secret store and omit it from checkpoints.

## Wait for compilation

```bash
curl --fail-with-body \
  "$PARA_SOCIAL_API/v1/linkedin/registrations/REGISTRATION_ID/status" \
  --header "Authorization: Bearer $PARA_API_KEY" \
  --header "X-Request-ID: linkedin-agent-status-001"

curl --fail-with-body \
  "$PARA_SOCIAL_API/v1/linkedin/registrations/REGISTRATION_ID/plan" \
  --header "Authorization: Bearer $PARA_API_KEY" \
  --header "X-Request-ID: linkedin-agent-plan-001"
```

Wait until `compilation_status` is `READY`. Require exactly ten unique search
plans, both rubrics, valid normalized weights, provenance for each hard filter,
and non-empty plan hashes. With `auto_activate: true`, also require
`auto_activation_status: ACTIVATED` and one ten-run cycle. Do not call activate
or run while compilation is pending.

## Manual activation and later runs

Call activate only when `auto_activate` was false:

```bash
curl --fail-with-body \
  --request POST \
  "$PARA_SOCIAL_API/v1/linkedin/registrations/REGISTRATION_ID/activate" \
  --header "Authorization: Bearer $PARA_API_KEY" \
  --header "X-Request-ID: linkedin-agent-activate-001" \
  --header "Idempotency-Key: activate:linkedin:founder-workflows:v1"

curl --fail-with-body \
  --request POST \
  "$PARA_SOCIAL_API/v1/linkedin/registrations/REGISTRATION_ID/run" \
  --header "Authorization: Bearer $PARA_API_KEY" \
  --header "X-Request-ID: linkedin-agent-run-001" \
  --header "Idempotency-Key: run:linkedin:founder-workflows:2026-07-29"
```

Each successful compiled activation or run creates exactly ten correlated runs.
Persist the cycle ID, all ten run IDs, and plan revision. A queue response is
not collection completion, and a manual run does not bypass delivery time.

## Monitor

Poll with bounded intervals:

```bash
curl --fail-with-body \
  "$PARA_SOCIAL_API/v1/linkedin/registrations/REGISTRATION_ID/status" \
  --header "Authorization: Bearer $PARA_API_KEY" \
  --header "X-Request-ID: linkedin-agent-status-001"
```

A cycle is terminal only after all ten query runs are terminal. Preserve
completed results and report partial failures with request ID, cycle ID, plan
revision, and per-query state.

## Consume results

```bash
curl --fail-with-body \
  "$PARA_SOCIAL_API/v1/linkedin/registrations/REGISTRATION_ID/batches?limit=25" \
  --header "Authorization: Bearer $PARA_API_KEY"

curl --fail-with-body \
  "$PARA_SOCIAL_API/v1/linkedin/registrations/REGISTRATION_ID/batches/BATCH_ID" \
  --header "Authorization: Bearer $PARA_API_KEY"
```

The immutable batch contains expanded post content, media and engagement text,
post/profile URLs, source query, initial and final relevance evidence, Parallel
author enrichment, and optional comment draft. `posts: []` is a valid completed
result.

## LinkedIn-specific boundaries

- Author context uses server-side Parallel enrichment after initial relevance.
- Only posts passing the server's first-pass threshold receive enrichment.
- Hard filters require explicit source provenance; unknown evidence is neutral
  and cannot hard-reject.
- Final scoring is deterministic from persisted post, author, company,
  geography, follower, and comment-opportunity components.
- Final selection deduplicates repeated queries, prior delivered URLs, and
  authors within the registration.
- Generated comment drafts are advisory and are not posted automatically.
- A separate browser, synthetic collector, or direct LinkedIn scraper is not a
  valid fallback.

[LinkedIn matching](/guides/matching-relevance) for score semantics.
