# PARA integration

PARA discovers and evaluates LinkedIn and Reddit posts. It can generate its own
drafts or accept revisioned drafts from another system. A draft remains a review
item until a dashboard user or a public API credential with `publishing:write`
explicitly approves it. Approval creates a durable publishing queue item; a
separately paired browser extension may post that approved snapshot later.

```text
GET /v1/me
  -> choose project and platform registration
  -> GET /v1/{platform}/registrations/{registration_id}/posts
  -> POST /v1/{platform}/registrations/{registration_id}/drafts
  -> human review in the dashboard or integrating system
  -> dashboard confirmation OR POST /drafts/{draft_id}/queue
  -> durable publishing queue
  -> assigned extension publishes the approved snapshot
```

`POST /drafts` is review intake and revision, not approval. The public queue
operation is an explicit approval that may lead to a later platform action. It
does not synchronously publish, and no public endpoint can claim extension work.

## Start here

Set the owner-scoped key in a secret store or environment variable. Never place
it in a URL, body, log, browser storage, checkpoint, or report.

```bash
export PARA_API_KEY='<issued-once-key>'
export PARA_API='https://para-linkedin-api.onrender.com'
```

Identify the key and all resources it can address:

```bash
curl --fail --silent --show-error \
  -H "Authorization: Bearer ${PARA_API_KEY}" \
  -H "X-Request-ID: identity-check-001" \
  "${PARA_API}/v1/me"
```

`GET /v1/me` works with any valid API key. It returns the owner, current
credential metadata, projects, and LinkedIn and Reddit registrations. Credential
metadata contains only `key_prefix`; key material is never returned.

## Resource model

```text
User -> Workspace -> Project -> Platform registration -> Current posts/drafts
                         |-> Connection assignment -> Profile -> Publishing queue
```

| Resource | Meaning |
| --- | --- |
| User | Dashboard login identity and public API owner |
| Workspace | Team and role boundary |
| Project | Cross-platform business initiative and publishing scope |
| Registration | One platform's discovery, matching, delivery, and draft-generation configuration |
| Current post | A post matched under the registration's current `matching_revision` |
| Batch | Immutable historical delivery snapshot |
| Review draft | Generated or external text awaiting an approval decision |
| Publishing item | Final dashboard- or API-approved text stored in the durable queue |

A project and a registration are not interchangeable. A project is the stable
business scope; a registration is the executable LinkedIn or Reddit discovery
definition inside it. A project currently has at most one LinkedIn registration
and one Reddit registration.

Use `GET /v1/projects` to page through explicit and compatibility projects. Each
item includes workspace metadata, project status, archive state, and registration
summaries. Public project creation is intentionally unsupported; create projects
in the dashboard.

`project_id` on registration creation selects an existing project. Omitting it
creates an implicit personal compatibility project for older integrations. A
public key selects an owner and scopes, not a project. New integrations should
resolve the intended project through `/v1/me` or `/v1/projects` and send its ID.

`external_id` is caller-owned reconciliation metadata. It is not a project ID or
registration ID. Reconcile by exact `external_id`; never guess an ID from a name.

## Credentials

PARA has three credential boundaries:

| Surface | Credential | Purpose |
| --- | --- | --- |
| Public API `/v1/*` | Owner API key | Identity, discovery, external draft revisions, and scoped queue approval |
| Dashboard `/api/*` | Dashboard access token | Project setup, human review, confirmation, queue inspection and cancellation |
| Extension `/api/extensions/*` | Paired device token | Collection or execution of already-approved queue items |

These credentials are not interchangeable. A public API key cannot be exchanged
for a dashboard session, but a key carrying `publishing:write` can use the public
external-draft queue operation.

Dashboard access begins at `POST /api/auth/login` on
`https://para-linkedin-scraper.onrender.com` with the person's email and
password. The returned access token is used only for dashboard `/api/*` calls.
Keep dashboard credentials out of public API integrations. Dashboard confirmation
remains available independently from public API approval.

Common scopes:

| Scope | Operations |
| --- | --- |
| `registrations:read` | Projects and registration reads |
| `registrations:write` | Registration mutations and external draft intake |
| `publishing:write` | Explicitly approve the active external draft into the durable queue |
| `batches:read` | Current normalized posts and historical batches |
| `deliveries:read` | Delivery inspection |
| `deliveries:write` | Delivery replay |
| `keys:manage` | API-key lifecycle |

Use a stable `Idempotency-Key` for each retryable mutation. External draft intake
and queue approval also require an explicit `X-Request-ID`. Reusing a key with the
same body returns the original response; reusing it with another body returns
`409`.

## Registration mode

Both platforms accept and return:

```json
{"mode":"discovery_only","draft_enabled":false}
```

| `mode` | Behavior |
| --- | --- |
| `discovery_only` | Collect, match, enrich, batch, and deliver; skip PARA comment generation |
| `draft` | Preserve the current discovery flow and generate PARA drafts |

`draft_enabled` remains supported for compatibility. Supplying either field
derives the other. Conflicting values return `422`. Omitting both defaults to
`mode: "draft"`. External draft intake works in either mode.

Registration lifecycle:

```text
GET    /v1/{platform}/registrations
POST   /v1/{platform}/registrations
GET    /v1/{platform}/registrations/{registration_id}
PATCH  /v1/{platform}/registrations/{registration_id}
POST   /v1/{platform}/registrations/{registration_id}/activate
POST   /v1/{platform}/registrations/{registration_id}/pause
POST   /v1/{platform}/registrations/{registration_id}/restore
POST   /v1/{platform}/registrations/{registration_id}/run
GET    /v1/{platform}/registrations/{registration_id}/status
DELETE /v1/{platform}/registrations/{registration_id}
```

LinkedIn compiler-native registrations may build a ten-search plan. Reddit
collection uses the assigned Reddit discovery extension. Collection is
asynchronous; wait for terminal run state before treating a cycle as complete.

## Read current posts

LinkedIn and Reddit now use the same operation and envelope:

```text
GET /v1/linkedin/registrations/{registration_id}/posts
GET /v1/reddit/registrations/{registration_id}/posts
```

Query parameters are `limit` from 1 to 100, opaque `cursor`, and optional
normalized `status`. The response is ordered by normalized score and stable ID:

```json
{
  "items": [{
    "post": {"id": "post-id", "url": "https://..."},
    "relevance": {
      "initial": {"status": "MATCH", "score": 0.68},
      "final": {"status": "MATCH", "score": 0.82}
    },
    "draft": {
      "id": "external-draft-id",
      "source": "external",
      "revision": 2,
      "status": "READY",
      "comment": "Review-ready text",
      "generated": {"source": "generated", "comment": null}
    },
    "score": 0.82,
    "status": "MATCH",
    "score_stage": "final"
  }],
  "next_cursor": null
}
```

Top-level `score` and `status` use final relevance when `final.score` exists;
otherwise they fall back to `initial.score` and its status. `score_stage` states
which source was used. If neither stage has a score, `score` remains `null` and
the item sorts after scored items. The list contains only the registration's current matching revision.
An active external draft is presented first; its nested `generated` field keeps
the PARA-generated draft provenance when one exists.

Do not parse cursors. Send `next_cursor` back unchanged. Use `/batches` for
immutable historical deliveries; current `/posts` and historical `/batches`
serve different purposes.

## Submit an external draft

Use the exact `post.id` from the current posts endpoint:

```bash
curl --fail --silent --show-error \
  -X POST \
  -H "Authorization: Bearer ${PARA_API_KEY}" \
  -H "Content-Type: application/json" \
  -H "X-Request-ID: draft-request-001" \
  -H "Idempotency-Key: draft-idempotency-001" \
  -d '{"post_id":"post-id","comment_text":"A useful, review-ready response."}' \
  "${PARA_API}/v1/linkedin/registrations/registration-id/drafts"
```

The same operation exists under `/v1/reddit`. LinkedIn text is limited to 3,000
characters; Reddit text is limited to 10,000 characters.

A successful response is `201` with a `READY` draft, immutable text snapshot,
revision, submitting credential ID, project, registration, post, and request ID.
It creates no publishing queue item and causes no extension action.

A new submission for the same current matched post changes the comment by creating
the next revision and marking the previous external revision `SUPERSEDED`. There
is no in-place `PATCH`: send the replacement `comment_text` to the same `/drafts`
endpoint with new request and idempotency keys, then use the new draft ID. The
newest `READY` revision becomes the review presentation. PARA-generated draft
fields remain unchanged. Cross-owner, unrelated, wrong-platform, or nonmatching
post IDs return an owner-scoped `404`.

## Approve into the publishing queue

Queue the exact active LinkedIn draft after the integrating system completes its
human review or other approval policy:

```bash
curl --fail --silent --show-error \
  -X POST \
  -H "Authorization: Bearer ${PARA_API_KEY}" \
  -H "Content-Type: application/json" \
  -H "X-Request-ID: queue-request-001" \
  -H "Idempotency-Key: queue-idempotency-001" \
  -d '{"confirm":true}' \
  "${PARA_API}/v1/linkedin/registrations/registration-id/drafts/draft-id/queue"
```

This operation requires `publishing:write`. Reddit uses the matching `/v1/reddit`
path and requires `{"confirm":true,"profile_id":"participation-profile-id"}`.
Only the newest `READY` external revision can be queued; a superseded draft returns
`409`. The server snapshots that draft's validated `comment_text` into the queue.
To change it, create a new draft revision first. The response is `201` with `QUEUED`,
the external draft ID, execution profile, approving credential ID, request ID,
and immutable comment snapshot.

The queue call is approval, not synchronous publishing. It can eventually cause
the assigned extension to post under the configured platform identity. Protect
`publishing:write` keys as action-authorizing credentials and do not grant that
scope to discovery-only consumers.

## Dashboard review

The dashboard automatically displays `READY` generated and external drafts on
the existing post cards. External drafts are labelled **External draft** and use
the same editable textarea. The reviewer may change the text before selecting
**Confirm to send**.

Dashboard confirmation requests may include the active external `draftId`:

```json
{
  "postId": "dashboard-post-id",
  "draftId": "external-draft-id",
  "commentText": "Final text approved by the reviewer"
}
```

LinkedIn uses `POST /api/linkedin/comment-queue?projectId={projectId}`. Reddit
also requires `profileId` and uses
`POST /api/reddit/comment-queue?projectId={projectId}`. Existing clients may omit
`draftId`; the server resolves the newest active external draft, then falls back
to the generated draft. A supplied stale or superseded `draftId` returns `409`.

Both approval paths store the final text, source kind, external draft ID, post,
project, registration, execution profile, and approving user or API credential in
Postgres. Later draft revisions cannot change that queue snapshot. Queue
cancellation does not delete the review draft.

Queue states are `QUEUED`, `CLAIMED`, `RETRY_WAIT`, `POSTED`, `FAILED`, and
`CANCELLED`. A server restart does not remove work. Only `POSTED` means the
platform action completed. The assigned posting or participation extension can
claim only approved, eligible queue items and remains subject to profile status,
identity checks, leases, pacing, daily limits, retries, and cancellation.

## Webhooks

Events are `linkedin.relevant_posts.daily.v1` and
`reddit.relevant_posts.daily.v1`. The signature is:

```text
v1=hex(HMAC_SHA256(webhook_secret, UTF8(timestamp + ".") || raw_body_bytes))
```

Use the exact raw request bytes, reject timestamps more than 300 seconds from
the receiver clock, compare digests in constant time, and durably deduplicate by
`X-Webhook-Id` before processing. Do not verify a parsed and re-serialized body.

```ts
import crypto from 'node:crypto';
import express from 'express';

type WebhookStore = {
  // Implement with a unique webhook-ID row and event writes in one DB transaction.
  processOnce(id: string, process: () => Promise<void>): Promise<'processed' | 'duplicate'>;
};

export function installParaWebhook(
  app: express.Express,
  secret: string,
  store: WebhookStore,
  processEvent: (payload: unknown) => Promise<void>,
) {
  app.post('/webhooks/para', express.raw({ type: 'application/json' }), async (req, res) => {
    const timestamp = String(req.header('X-Webhook-Timestamp') || '');
    const signature = String(req.header('X-Webhook-Signature') || '');
    const webhookId = String(req.header('X-Webhook-Id') || '');
    const timestampSeconds = Number(timestamp);
    if (!webhookId) return res.status(400).json({ error: 'missing_webhook_id' });
    if (!/^\d+$/.test(timestamp) || Math.abs(Date.now() / 1000 - timestampSeconds) > 300) {
      return res.status(401).json({ error: 'stale_timestamp' });
    }
    if (!/^v1=[a-f0-9]{64}$/i.test(signature)) {
      return res.status(401).json({ error: 'malformed_signature' });
    }
    const expected = crypto.createHmac('sha256', secret)
      .update(Buffer.concat([Buffer.from(`${timestamp}.`), req.body]))
      .digest();
    const provided = Buffer.from(signature.slice(3), 'hex');
    if (provided.length !== expected.length || !crypto.timingSafeEqual(provided, expected)) {
      return res.status(401).json({ error: 'invalid_signature' });
    }
    const result = await store.processOnce(webhookId, async () => {
      await processEvent(JSON.parse(req.body.toString('utf8')));
    });
    return res.status(result === 'duplicate' ? 200 : 204).end();
  });
}
```

## Errors and completion

Errors use `{error:{code,message,request_id,details}}`. Stop on `401`. On `403`,
request the missing scope. Treat `409` as a state or idempotency conflict and
`422` as invalid input. An empty `items` list is a successful read, not a failed
integration.

An external-drafting integration is complete only when it has:

1. Identified the owner, credential, project, and registrations through `/v1/me`.
2. Read a current post through the normalized `/posts` envelope.
3. Created or replayed one `READY` external review draft.
4. Verified that draft appears editable in the intended dashboard project.
5. Stopped unless a dashboard user separately confirms it.

Exact schemas and examples are in the
[live OpenAPI document](https://para-linkedin-api.onrender.com/openapi.json).
